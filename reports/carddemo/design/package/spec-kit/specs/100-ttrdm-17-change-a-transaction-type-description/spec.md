# Feature specification: Change a transaction type description

**Feature:** TTRDM-C17 · Transaction Type Reference Data Maintenance · Customer Data Setup

**Status: DRAFT**: the function is not signed off yet. Confirm with the owner before building to it.

## User scenarios and testing

### User story (TTRDM-C17)

As an administrator, I want to change a transaction type's description and confirm it before saving, so that the transaction type reference data stays correct.

An administrator changes a transaction type's description. The new description must be supplied and contain only letters, digits and spaces, up to 50 characters. The administrator confirms with F5 before it is written to the transaction type table, and can cancel with F12 before then. Nothing may be saved without that confirmation, a record lock must be reported as unsuccessful, and the screen must report the outcome of every save.

**Acceptance scenarios:**

1. **Given** stored description: Purchase; entered description: Purchases; key: Enter, **when** the operator presses Enter after changing the description of a displayed or new transaction type, **then** The description is validated; the state is 'E' until it passes (TTRDM-C17-AC-01)
2. **Given** Description: *, **when** the operator enters '*' or leaves the transaction type description blank, **then** The description is treated as not supplied. (TTRDM-C17-AC-02)
3. **Given** entered description: Cash back 2, **when** the changed description passes validation, **then** State 'N'; info message 'Changes validated.Press F5 to save' (TTRDM-C17-AC-03)
4. **Given** Original description: Purchase; New description: Purchase Retail, **when** the operator changes the shown or new details and the changes pass all edits, **then** The screen shows 'Changes validated.Press F5 to save'. (TTRDM-C17-AC-04)
5. **Given** Original description: Purchase; New description: purchase, **when** the operator changes the shown or new details and the changes pass all edits, **then** No change is detected; the details stay shown with 'No change detected with respect to values fetched.'. (TTRDM-C17-AC-05)
6. **Given** Screen state: awaiting confirmation (N); Key pressed: F5; Database result: success, **when** F5 is pressed while validated changes await confirmation (state 'N'), **then** 'Changes committed to database' is shown. (TTRDM-C17-AC-06)
7. **Given** Screen state: awaiting confirmation (N); Key pressed: F5; Database result: record locked (SQLCODE -911), **when** F5 is pressed while validated changes await confirmation (state 'N'), **then** State becomes lock error and 'Changes unsuccessful' is shown. (TTRDM-C17-AC-07)
8. **Given** Type: 07; Row exists: yes; Key pressed: F5, **when** the description update succeeds, **then** The change is committed and the screen shows 'Changes committed to database'. (TTRDM-C17-AC-08)
9. **Given** Type: 07; SQLCODE: -911, **when** the update cannot lock the row (SQLCODE -911), **then** The screen shows 'Changes unsuccessful' with the error 'Could not lock record for update', and nothing is committed. (TTRDM-C17-AC-09)
10. **Given** Screen state: awaiting confirmation (N); Key pressed: F12, **when** F12 is pressed while validated changes await confirmation (state 'N'), **then** Nothing is saved and 'Update was cancelled' is shown. (TTRDM-C17-AC-10)
11. **Given** Screen state: backed out (B); Key pressed: Enter; Details changed: no, **when** changes were backed out (state 'B') and the next input brings no new change, **then** State becomes changes not OK and 'Update transaction type details shown.' is shown. (TTRDM-C17-AC-11)
12. **Given** A transaction type's details are on screen for editing, **when** The operator clears the description (all spaces), or enters '*', and presses Enter, **then** The screen shows 'Transaction Desc must be supplied.', the state stays changes-not-OK ('E'), and no save is offered (TTRDM-C17-AC-12)
13. **Given** A transaction type's details are on screen for editing, **when** The operator changes the description to 'Cash-Advance!' and presses Enter, **then** The screen shows 'Transaction Desc can have numbers or alphabets only.', the state stays changes-not-OK ('E'), and no save is offered (TTRDM-C17-AC-13)
14. **Given** A changed description has been validated and is awaiting confirmation (state 'N'), **when** The operator presses F5 and the update of the transaction type table fails with a negative SQLCODE other than -911, **then** The error 'Error updating: TRANSACTION_TYPE Table. SQLCODE:' is shown, followed by the code and the database error text; the outcome is set to committed ('C') and the information message is 'Changes committed to database', not 'Changes unsuccessful' (TTRDM-C17-AC-14)

## Requirements

### Functional requirements

- **TTRDM-REQ-F-117** (business rule): When the operator presses Enter after changing the description of a displayed or new transaction type, the system shall mark the changes as not OK (state 'E') and then validate the description (up to 50 characters). Rules: TTRDM-BR-130.
- **TTRDM-REQ-F-118** (design note): When the operator enters '*' or leaves the transaction type description blank, the system shall treat the description as not supplied, and otherwise keep the entry with leading and trailing spaces removed. Rules: TTRDM-BR-131.
- **TTRDM-REQ-F-119** (business rule): If the changed description is blank (spaces or '*'), then the system shall show 'Transaction Desc must be supplied.' and keep the changes-not-OK state ('E'). Rules: TTRDM-BR-132.
- **TTRDM-REQ-F-120** (business rule): If the changed description contains any character other than letters, digits and spaces, then the system shall show 'Transaction Desc can have numbers or alphabets only.' and keep the changes-not-OK state ('E'). Rules: TTRDM-BR-133.
- **TTRDM-REQ-F-121** (business rule): When the changed description passes validation, the system shall move to changes-validated-awaiting-confirmation (state 'N') and show 'Changes validated.Press F5 to save'. Rules: TTRDM-BR-134, TTRDM-BR-135.
- **TTRDM-REQ-F-122** (business rule): When the operator changes the shown or new details and the changes fail an edit, the system shall move to changes not OK (state 'E'), and when nothing changed, the system shall keep showing the details. Rules: TTRDM-BR-135.
- **TTRDM-REQ-F-123** (business rule): When the operator presses F5 after the changes have been validated and are awaiting confirmation (state 'N'), the system shall update that type's description in the transaction type table and then show the outcome on the screen. Rules: TTRDM-BR-136, TTRDM-BR-137.
- **TTRDM-REQ-F-124** (business rule): When the description update succeeds, the system shall commit the change, set the outcome to committed ('C') and show 'Changes committed to database'. Rules: TTRDM-BR-138, TTRDM-BR-137.
- **TTRDM-REQ-F-125** (business rule): If the update cannot lock the row (SQLCODE -911), then the system shall set the outcome to lock error ('L'), show 'Changes unsuccessful' and give the error 'Could not lock record for update'. Rules: TTRDM-BR-139, TTRDM-BR-137.
- **TTRDM-REQ-F-126** (error handling): If the update fails with any other negative SQLCODE, then the system shall show the error 'Error updating: TRANSACTION_TYPE Table. SQLCODE:…' with the database error text, yet set the outcome to committed ('C') and show 'Changes committed to database' instead of 'Changes unsuccessful'. Rules: TTRDM-BR-140.
- **TTRDM-REQ-F-127** (business rule): If the save fails for any other database reason, then the system shall end in state 'F' showing 'Changes unsuccessful'. Rules: TTRDM-BR-137.
- **TTRDM-REQ-F-128** (business rule): When F12 is pressed while validated changes await confirmation (state 'N'), the system shall discard the pending save, show 'Update was cancelled' and mark the changes as backed out (state 'B'). Rules: TTRDM-BR-141.
- **TTRDM-REQ-F-129** (business rule): While changes are backed out (state 'B') and the next input brings no new change, the system shall return to changes not OK (state 'E') so the operator can edit again, keeping states 'E' and 'N' otherwise unchanged in the decision step. Rules: TTRDM-BR-142.

- DEF-030: Is this intended? The 'No input received' message for a blank search code can never be shown, because the blank check always sets 'Tran Type code must be supplied.' first. Also, the number check accepts signs and decimals, so '-5' is accepted as '05' and '.5' passes the not-zero check but is stored as '00'. (Subject-matter expert) On TTRDM-BR-131.
- DEF-066: Is this intended? When the update fails with an SQL error other than -911, or the insert of a new type fails, the program writes the SQL error text into the same field that holds the 'Update of record failed' flag. That flag is lost, so the program sets the outcome to committed and the screen shows 'Changes committed to database' alongside the error text. The failed outcome 'Changes unsuccessful' is never shown. In addition, the insert error message shows the update's SQLCODE (+100), not the insert's. (Subject-matter expert) On TTRDM-BR-136, TTRDM-BR-138, TTRDM-BR-139, TTRDM-BR-140.
- DEF-068: Is this intended? Several branches of the decision step can never run: after a save (state 'C') the program always resets to the search screen before the decision step, so its 'C -> show details' branch is dead; F12 never reaches the decision step with a validated key, so F12 never re-reads the table; the 'delete pending + F12' branch is shadowed by the earlier F12 branch; and the invalid-search-key state 'K' is overwritten by 'not fetched' immediately after it is set, so it never persists. The check for 'Invalid Key pressed. ' also tests a message nothing sets (the code that set it is commented out). (Subject-matter expert) On TTRDM-BR-142, TTRDM-BR-135, TTRDM-BR-141.

### Decision table gaps

- Outcome of saving a confirmed description change: R16 says the outcome is set to committed ('C') with 'Changes committed to database', while R31 says any other database failure ends in state 'F' with 'Changes unsuccessful'; an expert must confirm which outcome is intended.
