# Feature specification: Validate new transaction details

**Feature:** OATM-C32 · Online Account and Transaction Management · Customer Account Self-Service

**Status: FINAL**, signed off by Sam (acceptance), 2026-11-25.

## User scenarios and testing

### User story (OATM-C32)

As a staff user, I want every new transaction's fields checked for presence, numeric codes, amount format and real dates, with one clear message for the first problem, so that only complete and well-formed transactions are recorded.

Checks every field of a new transaction in a fixed order: the eleven mandatory fields, numeric type and category codes, the amount format -99999999.99, real YYYY-MM-DD origination and processing dates, and a numeric merchant ID. It stops at the first problem and shows only that field's message. Nothing may be saved while any check fails.

**Acceptance scenarios:**

1. **Given** Type CD: blank; Merchant Zip: blank, **when** Enter is pressed on the Add Transaction screen and the account or card number has passed its checks, **then** Only 'Type CD can NOT be empty...' is shown (OATM-C32-AC-01)
2. **Given** Type CD: 01; Category CD: blank; all other fields: filled in, **when** a mandatory transaction field is blank (spaces or low-values), **then** 'Category CD can NOT be empty...' is shown, the cursor is on Category CD, and no transaction is added (OATM-C32-AC-02)
3. **Given** Type CD: blank, **when** the transaction type code is blank, **then** 'Type CD can NOT be empty...' (OATM-C32-AC-03)
4. **Given** Type CD: 01; Category CD: blank, **when** the type code is entered and the category code is blank, **then** 'Category CD can NOT be empty...' (OATM-C32-AC-04)
5. **Given** Type CD: 01; Category CD: 0001; Source: blank, **when** the type and category codes are entered and the source is blank, **then** 'Source can NOT be empty...' (OATM-C32-AC-05)
6. **Given** Source: POS TERM; Description: blank; Amount: blank, **when** type, category and source are entered and the description is blank, **then** 'Description can NOT be empty...' (Description is checked before Amount) (OATM-C32-AC-06)
7. **Given** Description: Grocery purchase; Amount: blank, **when** type, category, source and description are entered and the amount is blank, **then** 'Amount can NOT be empty...' (OATM-C32-AC-07)
8. **Given** Amount: +00000050.00; Orig Date: blank, **when** all fields up to the amount are entered and the origination date is blank, **then** 'Orig Date can NOT be empty...' (OATM-C32-AC-08)
9. **Given** Orig Date: 2026-11-20; Proc Date: blank, **when** all fields up to the origination date are entered and the processing date is blank, **then** 'Proc Date can NOT be empty...' (OATM-C32-AC-09)
10. **Given** Proc Date: 2026-11-21; Merchant ID: blank, **when** all fields up to the processing date are entered and the merchant ID is blank, **then** 'Merchant ID can NOT be empty...' (OATM-C32-AC-10)
11. **Given** Merchant ID: 800000001; Merchant Name: blank, **when** all fields up to the merchant ID are entered and the merchant name is blank, **then** 'Merchant Name can NOT be empty...' (OATM-C32-AC-11)
12. **Given** Merchant Name: Corner Shop; Merchant City: blank, **when** all fields up to the merchant name are entered and the merchant city is blank, **then** 'Merchant City can NOT be empty...' (OATM-C32-AC-12)
13. **Given** Merchant City: Seattle; Merchant Zip: blank, **when** all fields up to the merchant city are entered and the merchant zip is blank, **then** 'Merchant Zip can NOT be empty...' (OATM-C32-AC-13)
14. **Given** all eleven fields: filled in, **when** all eleven mandatory transaction fields are entered, **then** No blank-field message; the type and category codes are checked next (OATM-C32-AC-14)
15. **Given** Type CD: AB, **when** the transaction type code is not numeric, **then** 'Type CD must be Numeric...' (OATM-C32-AC-15)
16. **Given** Type CD: 01; Category CD: 00X1, **when** the type code is numeric and the category code is not numeric, **then** 'Category CD must be Numeric...' (OATM-C32-AC-16)
17. **Given** Amount: 125.50, **when** the amount entered on the Transaction Add screen does not start with '-' or '+', followed by eight digits, a '.', and two digits, **then** 'Amount should be in format -99999999.99' is shown and nothing is saved (OATM-C32-AC-17)
18. **Given** Amount: +00000125.50, **when** the amount entered on the Transaction Add screen does not start with '-' or '+', followed by eight digits, a '.', and two digits, **then** The amount format check passes (OATM-C32-AC-18)
19. **Given** Amount: +00000125.50; Confirm: Y, **when** the amount passes the format check, **then** The transaction is stored with amount 125.50 (OATM-C32-AC-19)
20. **Given** Amount: -00000040.00; Confirm: Y, **when** the amount passes the format check, **then** The transaction is stored with amount -40.00 (OATM-C32-AC-20)
21. **Given** Orig Date: 2024/03/01, **when** the origination date entered on the Transaction Add screen is not in the form YYYY-MM-DD (four digits, '-', two digits, '-', two digits), **then** 'Orig Date should be in format YYYY-MM-DD' is shown and nothing is saved (OATM-C32-AC-21)
22. **Given** Orig Date: 2024-03-01, **when** the origination date entered on the Transaction Add screen is not in the form YYYY-MM-DD (four digits, '-', two digits, '-', two digits), **then** The format check passes (OATM-C32-AC-22)
23. **Given** Orig Date: 2024-03-01; Proc Date: 03-01-2024, **when** the processing date entered on the Transaction Add screen is not in the form YYYY-MM-DD, **then** 'Proc Date should be in format YYYY-MM-DD' is shown and nothing is saved (OATM-C32-AC-23)
24. **Given** Orig Date: 2024-02-30; Proc Date: 2024-03-01, **when** the origination date has the right form but the date-check service (CSUTLDTC) does not confirm it as a real calendar date (severity not '0000' and message number not '2513'), **then** 'Orig Date - Not a valid date...' is shown and nothing is saved (OATM-C32-AC-24)
25. **Given** Orig Date: 2024-02-29; Proc Date: 2024-03-01, **when** the origination date has the right form but the date-check service (CSUTLDTC) does not confirm it as a real calendar date (severity not '0000' and message number not '2513'), **then** The origination date is accepted (OATM-C32-AC-25)
26. **Given** Orig Date: 2024-03-01; Proc Date: 2024-13-05, **when** the origination date is accepted but the date-check service (CSUTLDTC) does not confirm the processing date as a real calendar date (severity not '0000' and message number not '2513'), **then** 'Proc Date - Not a valid date...' is shown and nothing is saved (OATM-C32-AC-26)
27. **Given** Merchant ID: ABC123456, **when** all earlier checks pass and the Merchant ID is not entirely digits across its 9 positions, **then** Rejected with 'Merchant ID must be Numeric...' (OATM-C32-AC-27)
28. **Given** Merchant ID: 12345 (followed by 4 blanks), **when** all earlier checks pass and the Merchant ID is not entirely digits across its 9 positions, **then** Rejected with 'Merchant ID must be Numeric...' (OATM-C32-AC-28)
29. **Given** Merchant ID: 123456789, **when** all earlier checks pass and the Merchant ID is not entirely digits across its 9 positions, **then** The check passes (OATM-C32-AC-29)
30. **Given** Orig Date: 2024-02-30; Proc Date: 2024-99-99, **when** Transaction Add screen runs, **then** Only 'Orig Date - Not a valid date...' is shown (OATM-C32-AC-30)

## Requirements

### Functional requirements

- **OATM-REQ-F-253** (business rule): When Enter is pressed on the Add Transaction screen and the account or card number has passed its checks, the system shall check the transaction fields for blanks in this order: Type CD, Category CD, Source, Description, Amount, Orig Date, Proc Date, Merchant ID, Merchant Name, Merchant City, Merchant Zip, and report only the first blank field. Rules: OATM-BR-269.
- **OATM-REQ-F-254** (business rule): If a mandatory transaction field is blank (spaces or low-values), then the system shall show that field's message, put the cursor on that field, redisplay the screen and save nothing. Rules: OATM-BR-270.
- **OATM-REQ-F-255** (business rule): If the transaction type code is blank, then the system shall show 'Type CD can NOT be empty...' with the cursor on the type code (TTYPCDI). Rules: OATM-BR-271.
- **OATM-REQ-F-256** (business rule): If the type code is entered and the category code is blank, then the system shall show 'Category CD can NOT be empty...' with the cursor on the category code (TCATCDI). Rules: OATM-BR-272.
- **OATM-REQ-F-257** (business rule): If the type and category codes are entered and the source is blank, then the system shall show 'Source can NOT be empty...' with the cursor on the source (TRNSRCI). Rules: OATM-BR-273.
- **OATM-REQ-F-258** (business rule): If type, category and source are entered and the description is blank, then the system shall show 'Description can NOT be empty...' with the cursor on the description (TDESCI). Rules: OATM-BR-274.
- **OATM-REQ-F-259** (business rule): If type, category, source and description are entered and the amount is blank, then the system shall show 'Amount can NOT be empty...' with the cursor on the amount (TRNAMTI). Rules: OATM-BR-275.
- **OATM-REQ-F-260** (business rule): If all fields up to the amount are entered and the origination date is blank, then the system shall show 'Orig Date can NOT be empty...' with the cursor on the origination date (TORIGDTI). Rules: OATM-BR-276.
- **OATM-REQ-F-261** (business rule): If all fields up to the origination date are entered and the processing date is blank, then the system shall show 'Proc Date can NOT be empty...' with the cursor on the processing date (TPROCDTI). Rules: OATM-BR-277.
- **OATM-REQ-F-262** (business rule): If all fields up to the processing date are entered and the merchant ID is blank, then the system shall show 'Merchant ID can NOT be empty...' with the cursor on the merchant ID (MIDI). Rules: OATM-BR-278.
- **OATM-REQ-F-263** (business rule): If all fields up to the merchant ID are entered and the merchant name is blank, then the system shall show 'Merchant Name can NOT be empty...' with the cursor on the merchant name (MNAMEI). Rules: OATM-BR-279.
- **OATM-REQ-F-264** (business rule): If all fields up to the merchant name are entered and the merchant city is blank, then the system shall show 'Merchant City can NOT be empty...' with the cursor on the merchant city (MCITYI). Rules: OATM-BR-280.
- **OATM-REQ-F-265** (business rule): If all fields up to the merchant city are entered and the merchant zip is blank, then the system shall show 'Merchant Zip can NOT be empty...' with the cursor on the merchant zip (MZIPI). Rules: OATM-BR-281.
- **OATM-REQ-F-266** (business rule): When all eleven mandatory transaction fields are entered, the system shall pass the blank check and go on to the numeric and format checks. Rules: OATM-BR-282.
- **OATM-REQ-F-267** (business rule): If the transaction type code is not numeric, then the system shall show 'Type CD must be Numeric...' with the cursor on the type code and save nothing. Rules: OATM-BR-283.
- **OATM-REQ-F-268** (business rule): If the type code is numeric and the category code is not numeric, then the system shall show 'Category CD must be Numeric...' with the cursor on the category code and save nothing. Rules: OATM-BR-284.
- **OATM-REQ-F-269** (business rule): If the amount entered does not start with '-' or '+', followed by eight digits, a '.', and two digits, then the system shall reject it with 'Amount should be in format -99999999.99' and save nothing. Rules: OATM-BR-285.
- **OATM-REQ-F-270** (design note): When the amount passes the format check, the system shall convert it to a signed number with two decimals, show it back in the form +99999999.99, and store that value as the transaction amount when the transaction is added. Rules: OATM-BR-286.
- **OATM-REQ-F-271** (business rule): If the origination date is not in the form YYYY-MM-DD (four digits, '-', two digits, '-', two digits), then the system shall reject the entry, show 'Orig Date should be in format YYYY-MM-DD' and save nothing. Rules: OATM-BR-287.
- **OATM-REQ-F-272** (business rule): If the processing date is not in the form YYYY-MM-DD, then the system shall reject the entry, show 'Proc Date should be in format YYYY-MM-DD' and save nothing. Rules: OATM-BR-288.
- **OATM-REQ-F-273** (business rule): If the origination date has the right form but the date-check service (CSUTLDTC) does not confirm it as a real calendar date (severity not '0000' and message number not '2513'), then the system shall show 'Orig Date - Not a valid date...' and save nothing. Rules: OATM-BR-289.
- **OATM-REQ-F-274** (business rule): If the origination date is accepted but the date-check service (CSUTLDTC) does not confirm the processing date as a real calendar date (severity not '0000' and message number not '2513'), then the system shall show 'Proc Date - Not a valid date...' and save nothing. Rules: OATM-BR-290.
- **OATM-REQ-F-275** (business rule): If all earlier checks pass and the Merchant ID is not entirely digits across its 9 positions, then the system shall reject the entry, show 'Merchant ID must be Numeric...' and put the cursor on Merchant ID. Rules: OATM-BR-291.
- **OATM-REQ-F-276** (business rule): The system shall stop the Transaction Add checks at the first failed check and show only that message, so a later check is made only after every earlier check has passed. Rules: OATM-BR-292.

### Decision table gaps

- Date checks: Rules do not say whether the Proc Date format check runs before or after the Orig Date real-date check, so which single message is shown is not settled.
- Date checks: No rule states the outcome when both dates pass apart from continuing to later checks (e.g. Merchant ID numeric); confirm the full check order.
