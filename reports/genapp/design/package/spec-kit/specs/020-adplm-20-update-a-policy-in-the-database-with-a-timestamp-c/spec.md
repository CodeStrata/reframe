# Feature specification: Update a policy in the database with a timestamp check

**Feature:** ADPLM-C20 · Application Deployment and Policy Lifecycle Management · Application Deployment Lifecycle Management

**Status: DRAFT**: the function is not signed off yet. Confirm with the owner before building to it.

## User scenarios and testing

### User story (ADPLM-C20)

As a policy administrator, I want a policy's product details and common details updated only when no one else has changed it since I read it, so that concurrent changes are not overwritten.

Updates a policy's product details (endowment, house or motor) and its common details (issue and expiry dates, broker and broker reference) only if no one else has changed the policy since the caller read it. The check compares the caller's last-changed timestamp with the stored one. It must never overwrite a concurrent change and never alter the payment recorded on the policy, and the caller must get the new last-changed timestamp back.

**Acceptance scenarios:**

1. **Given** Request data length: 0, **when** the policy update database program is called without any request data, **then** The message ' NO COMMAREA RECEIVED' is logged and the task ends with abend 'LGCA'; no policy is read or changed (ADPLM-C20-AC-01)

(ADPLM-C20-AC-04)

## Requirements

### Functional requirements

- **ADPLM-REQ-F-126** (error handling): If the policy update database program is called without any request data, then the system shall log the error ' NO COMMAREA RECEIVED' and end the task abnormally with code 'LGCA' (no dump), without attempting any database work. Rules: ADPLM-BR-136.
- **ADPLM-REQ-F-127** (design note): The system shall start each policy update with outcome '00' and use the request's customer number and policy number to find the policy to update. Rules: ADPLM-BR-137.
- **ADPLM-REQ-F-128** (business rule): When the policy row for the customer and policy number is read and its last-changed timestamp equals the one the caller supplied, the system shall update the endowment, house or motor details and then the common policy details, giving the policy a new last-changed timestamp. Rules: ADPLM-BR-138.
- **ADPLM-REQ-F-129** (business rule): When the policy row is found and its last-changed timestamp matches the caller's, where the request is a motor update ('01UMOT'), the system shall replace the motor record's make, model, value, registration, colour, CC, year of manufacture, premium and accidents with the request values, matching the record by policy number. Rules: ADPLM-BR-139, ADPLM-BR-140.
- **ADPLM-REQ-F-130** (business rule): When the policy row is found and its last-changed timestamp matches the caller's, where the request is a house update ('01UHOU'), the system shall replace the house record's property type, bedrooms, value, house name, house number and postcode with the request values, matching the record by policy number. Rules: ADPLM-BR-141, ADPLM-BR-142.
- **ADPLM-REQ-F-131** (business rule): When the policy row is found and its last-changed timestamp matches the caller's, where the request is an endowment update ('01UEND'), the system shall replace the endowment record's with-profits, equities, managed-fund and fund-name values, term, sum assured and life assured with the request values, matching the record by policy number. Rules: ADPLM-BR-143, ADPLM-BR-144.
- **ADPLM-REQ-F-132** (error handling): If the endowment, house or motor update finds no record for the policy number, then the system shall set outcome '01'. Rules: ADPLM-BR-145, ADPLM-BR-146.
- **ADPLM-REQ-F-133** (error handling): If the endowment, house or motor update fails for any reason other than a missing record, then the system shall set outcome '90' and write an error message with the date, time, customer number, policy number and SQL code, plus up to 90 bytes of the request, to the error log. Rules: ADPLM-BR-145, ADPLM-BR-147.
- **ADPLM-REQ-F-134** (error handling): If the endowment, house or motor update leaves an outcome other than '00', then the system shall close the policy retrieval and return to the caller without updating the common policy record or the policy file, and because the close resets the outcome, the caller receives '00' when the close succeeds. Rules: ADPLM-BR-148, ADPLM-BR-149.
- **ADPLM-REQ-F-135** (business rule): When the policy's last-changed timestamp matches the one in the request and no product-detail update has failed, the system shall set the policy's issue date, expiry date, broker ID and broker's reference to the request values and set its last-changed timestamp to the current database timestamp. Rules: ADPLM-BR-150.
- **ADPLM-REQ-F-136** (design note): When the policy record has been updated, the system shall read the new last-changed timestamp back, looking the policy up by policy number only, and return it to the caller in the request. Rules: ADPLM-BR-151.
- **ADPLM-REQ-F-137** (error handling): If reading back the new timestamp fails, then the system shall roll back the whole unit of work, set outcome '90' and log an error message with date, time, customer number, policy number, SQL code and the first 90 bytes of the request. Rules: ADPLM-BR-152.
- **ADPLM-REQ-F-138** (historical artifact): The system shall not store the request's payment amount during a policy update, so that a policy update never changes the payment (or commission) recorded on the policy. Rules: ADPLM-BR-153.
- **ADPLM-REQ-F-139** (business rule): If the caller's last-changed timestamp differs from the stored policy timestamp, then the system shall change no policy tables and set outcome '02', which the close that follows resets to '00' when it succeeds. Rules: ADPLM-BR-154.
- **ADPLM-REQ-F-140** (error handling): If no policy row matches the customer and policy number, then the system shall make no database update and set outcome '01', which the close that follows resets to '00' when it succeeds. Rules: ADPLM-BR-155.
- **ADPLM-REQ-F-141** (error handling): If reading the policy row fails for a reason other than not found, then the system shall set outcome '90' and write an error message with the SQL code to the error log, and the close that follows resets the outcome to '00' when it succeeds. Rules: ADPLM-BR-156.
- **ADPLM-REQ-F-142** (side effect): When the database update step finishes without an early return, including when the timestamps differ, the policy is not found or the policy read fails, the system shall pass the first 225 bytes of the request to the policy file update, which rewrites the policy file record with the details supplied, and then return to the caller. Rules: ADPLM-BR-157, ADPLM-BR-158.
- **ADPLM-REQ-F-143** (error handling): If the policy cursor cannot be opened, a product-detail update fails, the cursor cannot be closed, or the update was rolled back, then the system shall return to the caller without calling the policy file update. Rules: ADPLM-BR-159.
