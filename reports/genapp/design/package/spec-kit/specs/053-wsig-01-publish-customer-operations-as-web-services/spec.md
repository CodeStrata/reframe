# Feature specification: Publish customer operations as web services

**Feature:** WSIG-C01 · Web Service Interface Generation · Web Service Interface Generation

**Status: DRAFT**: the function is not signed off yet. Confirm with the owner before building to it.

## User scenarios and testing

### User story (WSIG-C01)

As an integration developer, I want the customer add, customer inquiry, customer update and customer number programs published as web services with their binding files and service descriptions, so that other applications can call customer operations as web services.

Publishes the four customer operations (add customer, customer inquiry, customer update and customer number lookup) as callable web services, each at its own fixed address with a published service description, so that other applications can work with customers without going through the screens. It serves integration developers and the systems they connect. It must never publish a service whose request or response layout differs from the layout the customer program actually uses, and it must never move a service address (GENAPP/LGACUS01, GENAPP/LGICUS01, GENAPP/LGUCUS01, GENAPP/LGICVS01) that callers depend on.

**Acceptance scenarios:**

1. **Given** program (PGMNAME): LGACUS01; request/response layout (REQMEM/RESPMEM): SOAIC01; URI: GENAPP/LGACUS01, **when** add-customer web service generation job runs, **then** A web service for adding a customer is generated, reached at GENAPP/LGACUS01 and calling LGACUS01 through a COMMAREA. (WSIG-C01-AC-01)
2. **Given** ZFSHOME: /u/genapp, **when** add-customer web service generation job runs, **then** Files /u/genapp/genapp/wsdir/LGACUS01.wsbind and LGACUS01.wsdl and log /u/genapp/genapp/logs/LS2WS_LGACUS01.LOG are produced. (WSIG-C01-AC-02)
3. **Given** program (PGMNAME): LGICUS01; request/response layout (REQMEM/RESPMEM): SOAIC01; URI: GENAPP/LGICUS01, **when** customer inquiry web service generation job runs, **then** A web service for inquiring on a customer is generated, reached at GENAPP/LGICUS01 and calling LGICUS01 through a COMMAREA. (WSIG-C01-AC-03)
4. **Given** ZFSHOME: /u/genapp, **when** customer inquiry web service generation job runs, **then** Files /u/genapp/genapp/wsdir/LGICUS01.wsbind and LGICUS01.wsdl and log /u/genapp/genapp/logs/LS2WS_LGICUS01.LOG are produced. (WSIG-C01-AC-04)
5. **Given** program (PGMNAME): 'LGUCUS01'; request and response copybook (REQMEM, RESPMEM): 'SOAIC01'; service address (URI): 'GENAPP/LGUCUS01', **when** customer update web service set-up job runs, **then** The customer update program is published as a web service at 'GENAPP/LGUCUS01' that passes its data through the COMMAREA. (WSIG-C01-AC-05)
6. **Given** program (PGMNAME): 'LGICVS01'; request copybook (REQMEM): 'SOAVCII'; response copybook (RESPMEM): 'SOAVCIO', **when** customer number web service set-up job runs, **then** The program that obtains a customer number from the VSAM file is published as a web service at 'GENAPP/LGICVS01'. (WSIG-C01-AC-06)
7. **Given** JAVADIR: 'java601_bit64_ga/J6.0.1_64'; HTTPPROXY: PROXY.HURSLEY.IBM.COM:80, **when** add-customer web service generation job runs, **then** The generation runs with that Java runtime and reaches external resources through the Hursley proxy. (WSIG-C01-AC-07)
8. **Given** TMPDIR: '/tmp'; TMPFILE: 'LS2WS', **when** customer inquiry web service generation job runs, **then** The generation uses /tmp for its temporary files named with prefix LS2WS. (WSIG-C01-AC-08)
9. **Given** the customer update web service generation for program LGUCUS01 is run with ZFSHOME set to the installation home directory, **when** the generation step completes, **then** the binding file '<ZFSHOME>/genapp/wsdir/LGUCUS01.wsbind', the WSDL '<ZFSHOME>/genapp/wsdir/LGUCUS01.wsdl' and the log '<ZFSHOME>/genapp/logs/LS2WS_LGUCUS01.LOG' all exist, at exactly those paths (WSIG-C01-AC-09)
10. **Given** the customer number web service generation for program LGICVS01 is run with ZFSHOME set to the installation home directory, **when** the generation step completes, **then** the binding file '<ZFSHOME>/genapp/wsdir/LGICVS01.wsbind', the WSDL '<ZFSHOME>/genapp/wsdir/LGICVS01.wsdl' and the log '<ZFSHOME>/genapp/logs/LS2WS_LGICVS01.LOG' all exist, at exactly those paths (WSIG-C01-AC-10)
11. **Given** the customer update generation step for LGUCUS01 is configured, **when** the step's generator settings are inspected before it runs, **then** it uses Java directory 'java601_bit64_ga/J6.0.1_64', CICS directory 'cics660', an empty path prefix, temporary directory '/tmp' and temporary file prefix 'LS2WS' (WSIG-C01-AC-11)
12. **Given** the customer number generation step for LGICVS01 is configured, **when** the step's generator settings are inspected before it runs, **then** it uses Java directory 'java601_bit64_ga/J6.0.1_64', CICS directory 'cics660', an empty path prefix, temporary directory '/tmp' and temporary file prefix 'LS2WS' (WSIG-C01-AC-12)

## Requirements

### Functional requirements

- **WSIG-REQ-F-001** (design note): The system shall expose the add-customer program LGACUS01 as a web service at relative address GENAPP/LGACUS01, passing data by COMMAREA and using the customer request and response layout SOAIC01 from library <SOURCEX>. Rules: WSIG-BR-001.
- **WSIG-REQ-F-002** (design note): The system shall write the add-customer binding file to <ZFSHOME>/genapp/wsdir/LGACUS01.wsbind, the service description to <ZFSHOME>/genapp/wsdir/LGACUS01.wsdl and the generation log to <ZFSHOME>/genapp/logs/LS2WS_LGACUS01.LOG. Rules: WSIG-BR-002.
- **WSIG-REQ-F-003** (design note): The system shall expose the customer inquiry program LGICUS01 as a web service at relative address GENAPP/LGICUS01, passing data by COMMAREA and using the customer request and response layout SOAIC01 from library <SOURCEX>. Rules: WSIG-BR-003.
- **WSIG-REQ-F-004** (design note): The system shall write the customer inquiry binding file to <ZFSHOME>/genapp/wsdir/LGICUS01.wsbind, the service description to <ZFSHOME>/genapp/wsdir/LGICUS01.wsdl and the generation log to <ZFSHOME>/genapp/logs/LS2WS_LGICUS01.LOG. Rules: WSIG-BR-004.
- **WSIG-REQ-F-005** (design note): The system shall generate the customer update web service for program 'LGUCUS01' with the CICS web service generation procedure (DFHLS2WS), using the COBOL copybook 'SOAIC01' for both request and response, service address 'GENAPP/LGUCUS01', COMMAREA data passing and proxy 'PROXY.HURSLEY.IBM.COM:80'. Rules: WSIG-BR-005.
- **WSIG-REQ-F-006** (design note): The system shall write the customer update binding file '<ZFSHOME>/genapp/wsdir/LGUCUS01.wsbind', the WSDL '<ZFSHOME>/genapp/wsdir/LGUCUS01.wsdl' and the log '<ZFSHOME>/genapp/logs/LS2WS_LGUCUS01.LOG'. Rules: WSIG-BR-006.
- **WSIG-REQ-F-007** (design note): The system shall generate the customer number web service for program 'LGICVS01' with the CICS web service generation procedure (DFHLS2WS), using COBOL request copybook 'SOAVCII' and response copybook 'SOAVCIO' from the source library, service address 'GENAPP/LGICVS01', COMMAREA data passing and proxy 'PROXY.HURSLEY.IBM.COM:80'. Rules: WSIG-BR-007.
- **WSIG-REQ-F-008** (design note): The system shall write the customer number binding file '<ZFSHOME>/genapp/wsdir/LGICVS01.wsbind', the WSDL '<ZFSHOME>/genapp/wsdir/LGICVS01.wsdl' and the log '<ZFSHOME>/genapp/logs/LS2WS_LGICVS01.LOG'. Rules: WSIG-BR-008.
- **WSIG-REQ-N-001** (design note): The system shall run the add-customer and customer inquiry generation with the CICS language-structure-to-WSDL procedure (DFHLS2WS), Java directory 'java601_bit64_ga/J6.0.1_64', CICS directory 'cics660', an empty path prefix, temporary directory '/tmp', temporary file 'LS2WS' and HTTP proxy PROXY.HURSLEY.IBM.COM:80. Rules: WSIG-BR-009, WSIG-BR-010.
- **WSIG-REQ-N-002** (design note): The system shall run the customer update and customer number generation with Java directory 'java601_bit64_ga/J6.0.1_64', CICS directory 'cics660', an empty path prefix, temporary directory '/tmp' and temporary file prefix 'LS2WS'. Rules: WSIG-BR-006, WSIG-BR-008.

### Needs clarification

- SME-107: When generating web service files fails (for example, a structure member is missing, the output directory can't be written, or the proxy can't be reached), what should happen: should the job fail, retry, or leave partial files behind? And when a job is run again, should it overwrite the existing binding, WSDL and log files or fail because they already exist? (Operations) On WSIG-BR-010, WSIG-BR-009, WSIG-BR-006.
- SME-108: The web service generation jobs use fixed settings from the legacy installation: Java directory java601_bit64_ga/J6.0.1_64, installation directory cics660, and HTTP proxy PROXY.HURSLEY.IBM.COM:80. Should the new system keep these values, replace them with equivalents, or make them configurable per environment? Is the proxy still needed at all? (Platform engineering) On WSIG-BR-010, WSIG-BR-009, WSIG-BR-006.
- SME-109: Output and log paths use the placeholders <ZFSHOME> and <SOURCEX>, and the source library is also a placeholder. What are the real base directory and source library in the target environment, and how should they be supplied to the new system? (Platform engineering) On WSIG-BR-010, WSIG-BR-009.
- SME-110: Once the binding file and service description have been generated, how are they deployed? Is deployment part of this business function or a separate process? (Integration team) On WSIG-BR-009.
- SME-113: Several generated binding files and WSDL files have no exact file names on record: add-policy Commercial, House and Endowment; inquiry House; customer update; update-policy Endowment and Commercial. Some recorded names also look irregular, such as 'HousePolicyWebServiceGenerationParameters' and 'WebServiceGenerationRequest.ws_bind'. What exact names must these files have for downstream consumers? Should they follow one convention, such as <service>.wsbind and <service>.wsdl? (Integration team) On WSIG-BR-006.
- SME-119: The customer update web service has an empty path prefix. Is that deliberate, or is it a placeholder that each environment should fill in? (Platform engineering) On WSIG-BR-006.
- SME-120: When the step that generates the web service definition (binding and WSDL) runs, what counts as success and what counts as failure? For example: what should happen if the request or response layout is invalid or incomplete, or if the output cannot be written, and may partial output be left behind after a failure? This applies to both the customer and the policy web service generation jobs. (Integration team) On WSIG-BR-008.
- SME-121: Where exactly should the new system read the source layouts from and write the generated web service files to? Today these locations are unfilled placeholders (<SOURCEX> and <ZFSHOME>). (Platform/infrastructure team) On WSIG-BR-008.
- SME-122: Environment settings used to generate the web services are currently fixed: the network proxy (PROXY.HURSLEY.IBM.COM:80), the Java runtime directory, the CICS install directory, and the source and output locations. Should these stay fixed or become configurable settings in the new system? (Platform operations team) On WSIG-BR-008.
- SME-123: The customer number web service takes a request (SOAVCII) and returns a response (SOAVCIO). What business information does each of these carry, that is, what does the published service actually expose to callers? (Business analyst) On WSIG-BR-008.
