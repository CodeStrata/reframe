# Reframe specification: pipeline 2, the Claude assessment and the comparison

Status: draft for the owner's agreement. Stories are built from it ([the plan](plan.md), pipeline 2, parts 2 to 4). Parts marked *(spike)* are settled by the spikes P2-04 and P2-05 before they are built.

## 1. Goal

After pipeline 1 has assessed a source with AWS Transform, Reframe:

1. assesses **the same source snapshot** (same SHA-256) with Claude's [code-modernization plugin](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization), with no help from AWS Transform's results;
2. keeps everything the plugin writes, as it wrote it;
3. generates, outside the plugin, requirements in the same shape as AWS Transform's from what the plugin found, each marked as generated by Reframe;
4. adds Claude's graph to the same Neptune cluster as AWS Transform's, marked as Claude's;
5. shows Claude's results in the same business review report as AWS Transform's;
6. builds a high-level page comparing the two, from the overview down to each domain, program and rule.

Both results are model output: two runs of either tool can differ. The comparison page says so.

## 2. Scope

In scope:

- the plugin's analysis steps, in this order: `modernize-preflight`, `modernize-assess`, `modernize-map`, `modernize-extract-rules`. They are the plugin's counterpart of AWS Transform's assessment: inventory and domains, structure and business flows, business rules.
- Claude Code run headless (`claude -p`) by Reframe's background worker, signed in with the person's Claude subscription (the default) or through Amazon Bedrock;
- a pipeline 1 run that has not been torn down, so its snapshot and Neptune graph are still there.

Out of scope: the plugin's planning and build steps (`modernize-brief`, `modernize-review`, `uplift`, `transform`, `reimagine`, `verify`, `harden`). The business review in the report takes the place of `modernize-review`.

## 3. Commands

| Command | What it does |
|---|---|
| `reframe claude [--run <id>] [--auth subscription\|bedrock] [--max-agents <n>]` | Runs stages C0 to C7 (below) on a pipeline 1 run, in the background worker. |
| `reframe compare [--run <id>] [--open]` | Builds the comparison page again from both results, and opens it. |

`reframe status`, `events`, `answer`, `resume`, `report` and `teardown` cover pipeline 2 as well. The home screen shows both pipelines for each run and has menu entries for both commands.

**The guided run.** In `reframe run`'s choices step, one more question: *After AWS Transform finishes, assess the same snapshot with Claude?* The default answer is yes. With yes, Reframe also asks how Claude signs in (section 4, stage C0) and the agent limit for rule extraction (stage C4), and the worker continues into pipeline 2 as soon as pipeline 1 is done. With no, the home screen suggests `reframe claude` once pipeline 1 is done.

## 4. Stages

Each stage records an intent before it starts and a receipt when it ends, in the same run folder as pipeline 1, so a stopped run resumes at the stage that stopped.

### Stage C0: preflight

Checked before anything runs, each failure stopping with the exact fix:

- pipeline 1 is done for the run, and the run is not torn down;
- Claude Code is installed and signed in for the chosen way:
  - **subscription** (default): the person's own Claude Code sign-in;
  - **bedrock**: Claude Code's Amazon Bedrock settings, either with the run's AWS profile and region or with a Bedrock API key the person has set in their environment. Reframe passes the key through to Claude Code and never writes it anywhere. *(spike: the exact settings and the models available in the region)*
- the plugin is installed at the pinned version;
- `python3` 3.8 or later, which the plugin's scripts need;
- the plugin's usage counts are turned off for Reframe's runs (`CODE_MODERNIZATION_TELEMETRY=0`): Reframe does not need them.

The guided setup offers to install or sign in to anything missing, only on a yes, as in pipeline 1.

### Stage C1: workspace

The workspace is `claude/` in the run folder:

- `legacy/<project>/`: the run's snapshot unpacked, read-only, after its SHA-256 is checked against the one pipeline 1 recorded. A different hash stops the run.
- `.claude/settings.json`: allows reading everything and writing only `analysis/`; denies edits under `legacy/` (as the plugin's README recommends).
- `analysis/<project>/INTENT.md`: written by Reframe, with the goal "understand it first", so the plugin asks nothing twice.

Nothing from AWS Transform's results is in the workspace, so Claude's assessment is independent of AWS's.

### Stage C2: plugin preflight

`modernize-preflight <project>`. Its five questions need a person (scope, build and test, bespoke build tooling, prior attempts, what is off limits):

- **autonomous**: Reframe answers from what it knows, each answer recorded with its reason in the decisions file: the complete source as snapshotted, analysis only, no build in this pass, a prior assessment by AWS Transform kept apart, nothing may change. Anything Reframe does not know is answered "Don't know".
- **interactive**: the person answers with `reframe answer`.

### Stage C3: assess and map

`modernize-assess <project>`, then `modernize-map <project>`. The map step also writes the plugin's interactive map page.

### Stage C4: rule extraction

Before `modernize-extract-rules <project>` starts, Reframe shows the plugin's estimate: shards, agents and tokens.

- In the guided run, interactive mode or the agent limit, the person confirms it.
- In autonomous mode, the run goes ahead only within `--max-agents`. An estimate above the limit stops the run and waits (`reframe answer`) with the estimate.
- The plugin's own question before a large run is answered the same way. *(spike: how the plugin asks headless, and where the estimate is read)*

A stopped extraction resumes with the plugin's own run ID, so finished agents are not paid for twice.

### Stage C5: retrieval

Reframe reads the plugin's outputs into its report model, keeping the files as written:

| File | Contents |
|---|---|
| `PREFLIGHT.md` | The five answers and the readiness checks |
| `ASSESSMENT.md` | Executive summary, inventory, domains, technical debt, security findings (credentials masked), documentation gaps |
| `topology.json` | Domains, modules with language and size, data stores, edges, entry points, business flows with personas |
| `BUSINESS_RULES.md`, `rules_result.json` | Rule cards: name, category, priority (P0, P1, P2), source `file:line`, plain English, Given/When/Then, parameters, edge cases, suspected defects, confidence, SME questions |
| `DATA_OBJECTS.md` | Core records and the rules that use them |
| `REPORT.html`, `TOPOLOGY.html` | The plugin's own pages, linked from Reframe's report |

At the end, the snapshot's hash is checked again, to prove nothing in `legacy/` changed.

### Stage C6: requirements generated by Reframe

One more headless Claude step, with Reframe's own prompt, turns the plugin's results into requirements in AWS Transform's shape: domain → business function → capability (a user story) → requirements (functional and non-functional, with their EARS pattern) → the rule cards behind each, and open questions with an owner.

- Its input is only the plugin's results, never AWS Transform's.
- Every requirement must cite at least one rule card or a `file:line` in the snapshot. One that cites neither is dropped and counted.
- Each requirement, function and capability is marked **generated by Reframe from Claude's results**, everywhere it is shown, and kept in its own file apart from the plugin's.

### Stage C7: Claude's graph in Neptune *(spike)*

Reframe loads Claude's map and rules into the run's Neptune cluster: domains, modules, data stores, flows and rules, and the edges between them. Each element carries the source (`claude`), the run, and the snapshot's SHA-256, so it is never mixed up with AWS Transform's.

- **A new graph** (created by pipeline 1): loaded, then checked with a query that counts what was loaded.
- **An existing cluster**: loaded only after the person's yes. Autonomous mode skips the load and records why. Teardown removes only the elements Reframe loaded, found by the run's ID, never by name.

The spike settles three things:

- what AWS Transform itself writes into the graph;
- the load format;
- how a load reaches the private cluster, for example from a function in the run's VPC using the existing bulk-loader role and the run's bucket.

Any component this needs is created by the project Terraform root with receipts, and removed by teardown.

### Stage C8: report and comparison

**Claude's business review.** The same report as stage 8 of pipeline 1, in its own tab:

- **Overview → domain → function → capability → requirement.** Requirements and functions are labelled "generated by Reframe from Claude's results". Under each requirement are the plugin's rule cards behind it (Given/When/Then, priority, confidence, source line).
- **Rule cards by domain and module**, exactly as the plugin wrote them.
- **SME questions as open questions**, with the plugin's confidence.
- **Technical detail:** inventory, debt, security, data objects, flows, and links to the plugin's own pages.

Review marks and their export work as in pipeline 1, and name the tool.

**The comparison page** (`outputs/comparison/index.html`) starts at the highest level and goes down:

1. **Overview:** the snapshot (source, commit, SHA-256), the date of each assessment, and the key numbers side by side: domains, functions, capabilities, requirements, rules (critical ones apart), open questions, programs covered.
2. **Domains:** each AWS Transform domain against the Claude domains sharing its programs, with the share of programs in common; domains that only one tool has.
3. **Programs:** for each program, which tool covered it and how many rules each found in it.
4. **Rules:** rules paired in two ways, each labelled with how it was paired:
   - **same program** (deterministic): rules from both tools that cite the same program, listed side by side;
   - **AI-paired**: a Claude step that reads both rule sets and proposes pairs, each with its reason and a confidence. It is marked as AI output, and a person can mark each pair right or wrong.
5. **Only one tool found:** rules, requirements and open questions without a match on the other side.

Every number links down to the items behind it in both reports. The page states that both results are model output.

### Teardown

`reframe teardown` also lists what pipeline 2 added:

- the components of stage C7;
- the graph elements Reframe loaded into an existing cluster.

It removes them with the same consent. The `claude/` workspace stays in the run folder with the rest of the run's records.

## 5. Run folder

In addition to pipeline 1's:

- `claude/`: the workspace (stage C1) with the plugin's outputs;
- `outputs/claude/`: the retrieved model, the generated requirements (stage C6), and Claude's business review;
- `outputs/comparison/`: the pairings and the comparison page.

## 6. Code layout

`src/reframe/claude/`: the Claude Code runner, the workspace, the plugin steps, retrieval, the generated requirements, the graph load. `src/reframe/report/` gains Claude's tab and the comparison page.

## 7. Acceptance

Pipeline 2 is done when, from the CLI only, on CardDemo:

- a guided run with the default answers goes through pipeline 1 and pipeline 2 with no input except the sign-ins and the agent limit, and builds both reports and the comparison page;
- the snapshot's SHA-256 is the same in both pipelines and unchanged after the Claude steps;
- Claude's graph is in the same Neptune cluster as AWS Transform's, marked as Claude's, and checked with a query;
- one run signs in through Amazon Bedrock instead of the subscription;
- `reframe teardown` removes everything both pipelines created, and the account is clean.
